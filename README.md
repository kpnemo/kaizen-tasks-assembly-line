# kaizen-tasks-assembly-line

The cross-repo harness and facilitator kit for the Kaizen Tasks workshop. It holds the workspace that contains the two application repos, the feature-request intake (six fields: Problem, Proposed behavior, Acceptance criteria, Out of scope, Looks or mockup — optional — and Your role), the readiness rubric, the triage and implement skills, the smoke package that gates promotion in both app repos, the seeded requests, and the runbook. It owns no application code.

Related repositories: [kaizen-tasks-api](https://github.com/kpnemo/kaizen-tasks-api), [kaizen-tasks-web](https://github.com/kpnemo/kaizen-tasks-web), [kaizen-tasks-product-skills](https://github.com/kpnemo/kaizen-tasks-product-skills).

## Set up the workspace

```bash
gh repo clone kpnemo/kaizen-tasks-assembly-line webapp
cd webapp
scripts/setup-workspace.sh
```

The script clones `backend/` and `frontend/` (both git-ignored here), selects Node 24 through nvm, checks that Postgres and Redis answer, creates the `kaizen_dev` and `kaizen_test` databases, runs `npm ci` in both repos, and prints the commands to start each app. Run it again any time; every step is idempotent.

## The three skills

Open Claude Code at the workspace root (`claude` in this folder). The skills are in `.claude/skills/`.

| Skill                  | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/seed-requests`       | Files `seeds/requests/*.md` as `feature-request` issues, skipping titles that already exist.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `/triage-requests`     | Scores every open `feature-request` issue with `rubric/readiness.md`, writes `triage/<date>.md`, applies score labels, upserts one comment per issue, rewrites the pinned Triage board, pushes the report to `develop`, and ends by asking the facilitator which issue to implement; it never starts implementing. `bug` issues are not scored: they go straight to `/implement-issue`. `--score-only <n \| file>` scores one request and writes nothing; `--dry-run` scores everything and writes nothing to GitHub. The rubric has three consumers now (this repo, product-skills, and the API's interview agent); each vendoring repo checks drift with its own `scripts/sync-rubric.sh --check`.                                                                                                                                                                                                                                                                            |
| `/implement-issue <n>` | Marks the issue `implementing`, creates the working branches through GitHub so they show under Development, then **briefs itself before it asks anything**: both app repos' `docs/product-map.md`, the web repo's `docs/ui-conventions.md`, every comment on the issue, any attached mockup, and one read-only pass over the code, written up as a briefing under `docs/superpowers/briefs/` and announced as a `Context gathered` comment. Then it routes the issue through the superpowers skills: a feature request goes **one** bounded round of at most four questions — each carrying the answer the agent recommends, and, when something visible changes, one design question offering two or three looks with a small mockup each — then approaches, spec, plan, and test-first execution with the API and web lanes running side by side, one implementer per repo, the API contract committed first; a bug goes to systematic debugging. Opens each repo's pull request as soon as its lane is clean, plus a docs-only one for the briefing, the spec and the plan here, and stops. It never merges. |
| `/auto-implement-issue <n>` | The same journey with nobody at the keyboard: no questions, no gates. The round is answered by Codex as the product owner's stand-in (recommended answers unless the issue says otherwise), the spec is reviewed by Codex and its must-fix items folded in, the plan runs in the two lanes, the pull requests open, and the skill waits for every check to turn green before it comments `Ready for staging: press "Deploy to staging" for #<n> on /pipeline.` and stops. Every assumption it took is listed in the briefing and in each pull request body. If it cannot finish, it says so on the issue (`Auto-implement stopped …`) and leaves the branches pushed. |

## Workflows

`.github/workflows/ci.yml` lints and typechecks the smoke package and validates the issue forms and the rubric.

`.github/workflows/issue-lifecycle.yml` keeps the labels in step with the issue's own state. The lifecycle is `implementing` → `staging` → `shipped`: `/implement-issue` sets `implementing` when it takes the issue into work, the app repos' `staging-label` workflow sets `staging` once every pull request for the issue is merged and staging serves them, and the facilitator adds `shipped` at ship time, immediately before closing the issue. On that close the workflow retires `implementing` and `staging`; on a not-planned or duplicate close it retires them without any `shipped`; on a reopen it removes `shipped` and puts `implementing` back.

It also undoes a close nobody asked for. A pull request opened from a GitHub-linked branch closes its linked issue on merge into the default branch even with no closing keyword, cross-repo included (proved 2026-09-10: issue #15, `kaizen-tasks-api#11`), and `develop` — the app repos' default branch — is staging. So an issue closed as completed while it still carries `implementing` or `staging` is reopened with a comment saying it closes at ship time. The primary fix is the repository setting **Auto-close issues with merged linked pull requests**, which must be off (there is no API for it; it is a pre-session eyes-on check); this is the net under it. A reopen by the job's own token raises no workflow event, so it cannot loop.

Two more details. The job reconciles against the issue read fresh (`gh issue view --json state,stateReason,labels`), not against the event payload, so a close followed quickly by a reopen cannot leave two jobs acting on stale snapshots. And "was this taken into work" is answered from the timeline (`labeled` events for `implementing` or `staging`) when the labels no longer say, so a reopen after a not-planned close restores the right state. Because it is an `issues` workflow, GitHub always runs the copy on the repository's **default branch**, which here is `develop` — it is live as soon as it merges there, and needs no promotion to `main`. No step in the runbook or in either skill touches these labels by hand except the Ship step's `shipped` and the failure-page recovery. And no pull request in either app repo carries a closing keyword (`Part of kpnemo/kaizen-tasks-assembly-line#<n>`, never `Closes`), because merging into `develop` is staging and the issue closes only at ship time (`docs/runbook.md`, Ship).

## Smoke package

`smoke/` is a Playwright test that registers a user, creates a task, waits for the assistant, accepts a suggestion, and logs out; it also asserts the footer prints the version the API reports. Promote a smoke change to `main` only after the app change it asserts on is live on staging, since both app repos' `promote` gates run whatever `main` holds. Both app repos check this repository out at `main` and run it against staging in their `promote` workflow. See `smoke/README.md`. Because `promote` reads `main`, not `develop`, `main` must be re-pointed at `develop` after any change to `smoke/` — verify with `gh api 'repos/kpnemo/kaizen-tasks-assembly-line/contents/smoke/package.json?ref=main' --jq .name`, expecting `package.json`.
