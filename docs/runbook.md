Time budget inside the Implement segment: the briefing is the only new cost, and it is bounded to three minutes from the `Brief start:` line it prints when it begins — taking the issue into work is not charged to it, and the 25-minute time box still runs from `Start:`. Both product maps are built beforehand and checked in the pre-session list, so nothing is generated live — only the single code exploration runs during the session, and it is asked for about a minute. If it overruns, Esc is the escape hatch (section 4) and the briefing carries on without it.

**What the two buttons do.** Both appear only for facilitator accounts (emails on `FACILITATOR_EMAILS` on the API), and each opens a confirmation that says exactly what will happen and asks for the deploy passphrase (`DEPLOY_PASSPHRASE`; five wrong attempts lock the account for ten minutes). **Deploy to staging** appears on an issue at stage `Implementing` once every one of its open pull requests is green, and merges them api → web → harness with the head it inspected; the app repos' `staging-label` workflow then comments on the issue and moves the label, and the row's chip follows. **Deploy <version> to production** appears on every issue at stage `Staging` and dispatches this repository's `ship` workflow with that version and every such issue: the run cuts both releases, merges them on `ci`, waits for staging, opens the promotion pull requests, merges them on `ci` and `promote` (api first), reads production back by merge SHA, and closes the issues as `shipped`. While it runs the row reads `Shipping: <step>` with a link to the run; a failed run comments `Ship failed at <step>` on the issue, the row shows the same with a **Retry** button, and the rerun resumes at the step it reached. The page polls every ten seconds and the API's snapshot is at most thirty seconds old, so a change takes up to forty seconds to show; the badges and the chip, not a terminal, are the read-back the room sees. Dry-run the workflow before the session (`dry_run` on, from the Actions tab) and check `SHIP_TOKEN` is present (`gh secret list --repo kpnemo/kaizen-tasks-assembly-line`).

**Two waits in that block are not padding.** `wait_for_gates` before each promotion: a pull request's checks register a few seconds after it exists, so `gh pr checks --watch` run straight after `gh pr create` finds nothing to watch and returns at once, and `main`'s branch policy then refuses the merge for missing `ci` and `promote` — that cost a retry in the 2026-09-10 dry run. It waits for those two **by name**, because counting entries is not enough: Railway's own check plus `ci` already make two while `promote` is still absent. It gives up after two minutes and says so rather than merging blind. The `for` loop after the close: `gh issue close` returns before Actions has even queued the run, so a read-back on the next line shows the old labels and looks like a failure on the projector.

**No pull request may close the issue, and there are two ways one could.** The first is a closing keyword; no pull request carries one any more, every body says `Part of kpnemo/kaizen-tasks-assembly-line#<n>`, which is a plain timeline cross-reference (the Development panel is fed by the branches `/implement-issue` linked, not by that line). The second is the linked branch itself: a pull request opened from a branch linked to the issue closes it on merge into the default branch with no keyword at all, across repositories — proved on 2026-09-10 with issue #15 and `kaizen-tasks-api#11`, which closed it one second after the merge. `develop` is that default branch in both app repos, so the merge to staging is the danger, exactly as it was for #11 in the dry run.

Three things hold the line, in order: the repository setting **Auto-close issues with merged linked pull requests** is off (pre-session checklist); the `ship` workflow (and the appendix's close) adds `shipped` before it closes, which is how the lifecycle workflow tells a real ship from an accident; and if an issue still in work is closed without `shipped`, `.github/workflows/issue-lifecycle.yml` reopens it with a comment saying why. On a real ship that same workflow retires `implementing` and `staging`, so there is no label to flip by hand. When the API changed too, merge and promote the API pull request first, then the web one.

## 3. What to say at each gate

**The failing test.** "Nothing was written yet. The agent wrote down what done means as a test, ran it, and it fails. That failure is the specification. When it passes, the acceptance criterion you wrote in the form is met, not approximately, exactly."

**The docs-check gate.** "The agent tried to finish and the harness said no. Look at the message: the changelog is missing an entry, or the API contract was not regenerated. This is the same check CI runs, so a shortcut here fails the pull request there. Documentation is part of the change, not a follow-up."

**The in-app request interview.** "The assistant, the PM's own local skill, and engineering's triage all score readiness from the same rubric text, so what you see rising here is the same number triage will read. The transcript folded into the issue is the handover: engineering sees not just the final request but how it got there."

**The briefing.** "It read the product and the code before asking anything: both repos' product maps, the whole issue thread, any screenshot you attached, and one pass over the code. Every question left is one the issue really does not answer. And the map it read regenerates itself — a stale map cannot merge."

**The round.** "The agent is interviewing the product owner, not the engineer. One round, at most four questions, and every one of them arrives with the answer the agent would give — so I can answer them, or I can say 'take your recommendations' and take all of them, rewordings included. Each is a question the tester would otherwise have asked later, after the code was written. There is no second round. And if I short-cut with 'use the issue text' and that leaves a criterion nobody can test, it stops and asks me that one thing rather than guessing."

**The design question.** "It is not asking which component to use. It is asking what you want to see: two or three options, each with a sketch, drawn from the web repo's own UI conventions, recommended one first. If your request already said how it should look, it shows that back for a yes instead of offering a menu. And it comes back at the end as a screenshot of both themes on the pull request."

**The spec and the plan.** "We agree on the words before the code. The spec is what we said done means; the plan is what the reviewer holds the code to. Both are files in the repository, both take one yes from me."

**The pull request.** "Here is the diff, the tests, the evidence, and the link to your issue. The agent stops here. A person merges. In this room that person is me, and I only merge because the checks are green: the button that merges does not appear until they are."

**CI on develop.** "Actions runs lint, types, tests against a real database, the docs check, the build. If any fails, nothing deploys."

**Railway waits for CI.** "Railway has already seen the commit. It is holding the deployment until GitHub says the checks passed. A red check never reaches staging."

**Staging health.** "`/version.json` and `/api/v1/health` report the commit hash. The pipeline does not guess whether the build is live; it reads the hash."

**The promote check.** "A browser is registering a user, creating a task, waiting for the assistant, accepting a step, logging out, against staging, right now. Only if that passes may `main` merge."

**Production.** "The same hash, on the production URL. Idea to production, with tests and gates, in under an hour."

**Closing the issue.** "No pull request closed this. Merging to `develop` is staging, so a `Closes` line there would have closed your request an hour too early. The ship workflow closed it just now, after reading production back, with one comment that writes both versions and the URL onto the issue. Watch the labels go `implementing` → `staging` → `shipped` across the last twenty minutes: I typed none of them. I pressed two buttons."

**The footer version.** "The footer reads the version and commit of both halves; when they differ during a rollout, the API part turns amber, and the smoke test refuses a promotion where they disagree."

## 5. Rollback

Dashboard: open the project `kaizen-tasks`, select the environment, click the service, Deployments tab, find the previous deployment with a green check, open its menu, Redeploy. It is live within about a minute; `/version.json` or health shows the previous commit.

Why it is safe: migrations are additive only (API ADR 0004), so the previous application runs against the already-migrated database, and API changes are additive, so the previous web build keeps working against a newer API. Rollback never touches data.

After a rollback the footer shows the previous version and the API part goes amber until both halves are rolled back or re-promoted together.
