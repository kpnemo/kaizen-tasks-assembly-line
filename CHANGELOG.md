### Added

- `.claude/skills/auto-implement-issue/SKILL.md`: `/auto-implement-issue <n>`, the unattended variant of `/implement-issue` (#36). It reads `implement-issue` from disk and runs it under an override block: no AskUserQuestion, no gates; the round is answered by Codex as the product owner's stand-in (`codex-companion.mjs task --background`, read-only, bounded by `status --wait --timeout-ms`, recommended answers on any fallback), the spec is reviewed by Codex and its must-fix items folded in and marked **(review)**, the ADR on `arch-change` is written without confirmation, the plan runs in the two lanes, the pull request bodies carry `## Assumptions` and `## Codex review`, and a new Step 11 watches every pull request's checks (15 minutes each, one fix round) before commenting `Ready for staging: press "Deploy to staging" for #<n> on /pipeline.` Its only other endings are `Auto-implement stopped at <lane> Task <n>: …` and `Auto-implement stopped: checks red on <url>`. Prompt templates `round-prompt.md` and `spec-review-prompt.md` beside it.
- `.claude/skills/implement-issue/SKILL.md`: the plan is written in lanes, one per repo (`## Lane API`, `## Lane Web`, optional `## Lane Harness`), with task numbers unique across the plan, a contract-first Task 1 that is the only task allowed to touch `openapi.json`, and a `## Joins` block; Step 7 gains "Two lanes": a two-lane plan executes with `superpowers:subagent-driven-development` as the controller, one implementer per lane running side by side (never two in one repo), reviews packaged per lane with `git -C <repo>`, one lane-prefixed ledger, the API dev server started from the finished API branch before the web screenshot task; Step 8 opens each repo's pull request as soon as its lane's final review is clean (#36).

- `.claude/skills/implement-issue/SKILL.md` Step 2b, "Brief": before any question the request path reads both app repos' `docs/product-map.md`, the web repo's `docs/ui-conventions.md`, the issue body and **every** comment on it (later comments override earlier ones; no triage comment is not a blocker), downloads up to four attached images with `curl --max-time 10 --max-filesize 5000000` into the git-ignored `.superpowers/briefs/<n>/` and looks at each with the Read tool, and dispatches **one** read-only Explore subagent at breadth `medium` with a 60-second budget and a 25-line cap in its prompt, waiting for its result (the facilitator presses Esc if it runs past two minutes, and the briefing then continues on the maps alone with `exploration: skipped` under Unknowns). It prints `Brief start: <HH:MM>` and has an aggregate deadline of three minutes from that line, while the 25-minute time box still runs from `Start:`. It degrades gracefully when Part A and Part B have not merged yet: a missing product map or `ui-conventions.md` is noted in the briefing and the run continues, and a repo without a `product-map` script is skipped with one line at Step 7. The harness branch is created on the request path only, so a bug leaves this checkout on `develop` and `/triage-requests` can still push its report. classifies the request `UI: visible` or `UI: none` and the repos touched, writes `docs/superpowers/briefs/<date>-issue-<n>-<slug>.md`, and posts the milestone comment `Context gathered: touches <areas>; today <one line>; open questions: <k>.`
- `.github/ISSUE_TEMPLATE/feature-request.yml`: an optional `looks` textarea, "Looks or mockup (optional)", between Out of scope and Your role. The request form has six fields now; `scripts/check-issue-form.mjs` carries the new ordered id list and the bug form is unchanged. The rubric is untouched: clarity is still scored from the acceptance criteria alone. In-app intake is unchanged.
- `docs/runbook.md` pre-session checks: both product maps fresh (`npm run product-map && git diff --exit-code docs/product-map.md` in each app repo) and the screenshot capture rehearsed once on the laptop (`node scripts/screenshot.mjs tasks` in the web repo, then look at the two PNGs). Section 3 gains gate lines for the briefing, the round and the design question; section 4 gains a row for a briefing still running past its three minutes.
- `.gitignore`: `.superpowers/`, the scratch directory the briefing downloads attachments into. Nothing in it is ever committed.

- `.github/workflows/issue-lifecycle.yml`: the labels follow the issue state. The facilitator adds `shipped` and then closes at ship time; the workflow retires `implementing` and `staging` on that close, retires them without `shipped` on a not-planned or duplicate close, and on a reopen removes `shipped` and restores `implementing` when the issue had been taken into work. It also reopens, with a comment, any issue closed as completed while it still carries `implementing` or `staging` — a pull request from a GitHub-linked branch closes its linked issue on merge into the default branch with no closing keyword at all, cross-repo included (proved 2026-09-10 with issue #15 and `kaizen-tasks-api#11`), and `develop` is that branch; the repository setting "Auto-close issues with merged linked pull requests" being off is the primary fix and this is the net under it. It reconciles against the issue read fresh rather than the event payload, and decides "was it taken into work" from the timeline's `labeled` events when the labels no longer say — read with `--paginate --slurp` piped to `jq`, since gh's own `--jq` runs per page and would print one count per page on any timeline past 30 events.
- The `staging` label in `scripts/setup-labels.sh` ("Every pull request for the issue is merged and staging serves them"), the middle of the three lifecycle states `implementing` → `staging` → `shipped`. It is applied by the app repos' `staging-label` workflow, which needs the `ASSEMBLY_LINE_TOKEN` secret in both app repos.
- Bug intake: `.github/ISSUE_TEMPLATE/bug-report.yml` (What happened, What you expected, Steps to reproduce, Where, Your role; label `bug`), the `bug` label in `scripts/setup-labels.sh`, a contact link in `.github/ISSUE_TEMPLATE/config.yml`, and `scripts/check-issue-form.mjs` extended to validate both forms.
- `docs/playbook.md`: the one-page second-screen cheat sheet for Part 1, each step as type, see, say, with an "If it breaks" block and the numbers to keep in mind.
- Facilitator runbook (`docs/runbook.md`): pre-session checklists, the Part 1 minute-by-minute table, gate scripts, a failure page, rollback, and the Part 2/3 handoffs.
- `scripts/check-versions.sh`: checks that `backend/package.json` and `frontend/package.json` carry the same version, for the shared-versioning convention across the app repos.
- `smoke/tests/smoke.spec.ts` step 1b: asserts the web footer prints the version and short commit reported by `GET /api/v1/health`.

### Changed

- `.claude/skills/implement-issue/SKILL.md`: Step 5 is now **one** round. It invokes `mattpocock-skills:grilling` with an explicit override block stated as workshop instructions that take precedence — exactly one round, no subagents (the facts are in the briefing), no separate "shared understanding" confirmation, at most four numbered questions each carrying its recommended answer, and the round ends the moment the product owner answers or says `take your recommendations` or `use the issue text`. The two escape hatches no longer contradict the untestable-criterion stop: both end the questioning, `take your recommendations` accepts the proposed testable rewordings so progression is guaranteed, and `use the issue text` may leave a blocker, in which case the skill stops with that one criterion and its question. The runbook and the playbook say the same. Step 3 now restates the **effective** acceptance criteria — the form's section with every later decision from the issue thread applied, each replacement, addition or strike citing the comment that made it — and maps those to tests, so a criterion the requester changed in a reply is no longer tested against the form's original wording; the spec and the pull request checklist use that list, not the form's text. The round is built as one deduplicated list cut to four rather than three sources added together: the design question's slot is reserved first when the request is visible, then the blockers, then the briefing's open questions, and blockers are combined into one question rather than dropped when the slots are short. Step 3's untestable criteria stop being a stop and lead that round with a recommended testable rewording; only an answer that still leaves one untestable stops the path. When the request is `UI: visible` one of the four questions is a design question, asked through AskUserQuestion with two or three options, the recommended one first, and the small text mockup in each option's `preview` field (only `preview` renders side by side; `description` is a truncated one-liner) — and confirmation-only, showing the request's own design back, when the issue already carries a mockup or names a look. `superpowers:brainstorming` is then started at the approaches. The spec gains a `Context:` line pointing at the briefing and, for visible changes, a `## Looks` section (control, icons, placement, both themes); the plan's web task carries the screenshot step and the pull request body embeds the PNGs with commit-pinned `raw.githubusercontent.com` URLs, or the single line `Screenshot unavailable: <reason>`. The harness branch `feat/<n>-<slug>` moves from Step 5 to Step 2 so the briefing has a branch to live on; Step 7's command block runs `npm run product-map` before the checks (after `npm run openapi`, which feeds it); Step 8 stages the briefing with the spec and the plan and the docs pull request names all three; Step 9's audit expects the briefing and the `Context gathered` comment; the milestone table gains the `Context gathered` row and `Interview done` becomes `Interview done: <k> questions, <r> recommendations taken; approach chosen: <one line>.`
- `docs/runbook.md` and `docs/playbook.md`: step 7 is one round with recommended answers, ended by answering or by "take your recommendations" or by "use the issue text", plus the design question when the request changes something visible; `Context gathered` joins the issue timeline; the briefing's what-to-say line is "It read the product and the code before asking; every question left is one the issue really does not answer"; and the time budget says the briefing costs at most three minutes because the maps are built beforehand and only the single code exploration runs live.
- `.claude/skills/triage-requests/SKILL.md`: says that a fetched request body may now carry a `Looks or mockup` section, and that it is context for complexity and risk only — clarity is still scored from the acceptance criteria alone.
- `README.md`: the `/implement-issue` row describes the briefing, the one bounded round and the design question; the intake is described as six fields; the docs list names `docs/superpowers/briefs/`.
- `.claude/skills/implement-issue/SKILL.md`: no pull request in either app repo carries a closing keyword any more. Every body says `Part of kpnemo/kaizen-tasks-assembly-line#<n>`, because merging into `develop` is staging, not production, and the issue must close only at ship time; the branch slug collapses runs of non-alphanumerics (`feat/11-add-light-dark-and-system-theme-toggle`, not `...light--dark--and...`); the docs gate is run as `BASE_SHA=$(git merge-base origin/develop HEAD) bash scripts/docs-check.sh --ci`, since `npm run docs:check` is the `--hook` form and `--ci` without `BASE_SHA` either refuses to run (API) or silently diffs only `HEAD~1` (web); a new "contract ripple" checklist walks `docs/API.md`, the README route table, the web contract pull, the ADR the pull always needs, and the auth-store user literal; and "one gate, one confirmation" states that `arch-change` is the only ADR that stops for a human.
- `docs/runbook.md` and `docs/playbook.md`: the Ship block labels the issue `shipped` and then closes it explicitly, after the production read-back, with `gh issue close --reason completed --comment "Shipped in api <version> (<sha>) and web <version> (<sha>): <production url>"`, waits up to 90 seconds for the lifecycle workflow to retire `implementing` and `staging` rather than racing it, and flips the Triage board row to `shipped`. Each promotion pull request now waits, through a bounded `wait_for_gates` helper, for `ci` and `promote` to register **by name** (two minutes, then it stops the promotion with a message) before `gh pr checks --watch`, because `--watch` on a pull request whose checks have not registered returns at once and `main`'s branch policy then refuses the merge — and counting entries is not enough, since Railway's own check plus `ci` already make two. The runbook gains pre-session checks for the workflow, the `staging` label, `ASSEMBLY_LINE_TOKEN` in both app repos and the auto-close repository setting, plus failure-page rows for labels that did not move, a self-reopened issue and a missing `staging`; the playbook gains the matching "see" lines.

It creates the working branches through GitHub (`createLinkedBranch`, ids resolved at run time) so they appear under Development on the issue, flips the chosen issue's row on the Triage board, posts one short milestone comment per stage (taken into work, interview done, spec and plan approved, pull request opened) so the issue timeline carries the whole journey, creates the docs branch before brainstorming so the spec and plan commit onto it, forbids `superpowers:using-git-worktrees` and `superpowers:finishing-a-development-branch`, runs the docs gate in its CI form after the commit, and opens the spec and plan as a third, docs-only pull request. It still never merges.
